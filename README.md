# Bitwallet

Bitwallet is a **multi-chain crypto wallet prototype** — a polished,
professional-feeling wallet website built for demo and portfolio purposes.
It is a plain static website (HTML, CSS, vanilla JavaScript) that talks
directly to Firebase from the browser. There is no build step and no
server.

## This is a simulated wallet

- **No real cryptocurrency is stored, sent, or received.** Every balance,
  price, gas fee, and transaction is generated by the app itself and
  stored in your own Firestore project.
- **No real private keys or seed phrases exist anywhere in this app.** The
  "recovery phrase" screen under Settings uses obviously synthetic
  placeholder words, included only to demonstrate the UI.
- **No blockchain is ever contacted.** Sending, receiving, and balances
  are simulated entirely in Firestore.
- **Balances are configurable.** New users get a starting demo portfolio,
  and an admin panel lets an authorized admin reconfigure any user's
  simulated wallet.
- **Deposits and withdrawals in the real-world sense are not supported.**
  Send/Receive only ever move numbers around inside your Firestore data.

Real Firebase Authentication is used for accounts — login/logout is a
genuine (not simulated) part of the demo.

## Why this is a static website, not a React app

There is no framework, no bundler, and no `npm install` required to run
the finished site. It is plain HTML/CSS/JS that any static file host
(including GitHub Pages) can serve as-is. Firebase is loaded straight
from Google's CDN using the modern **modular** Firebase Web SDK.

## Routing

Because GitHub Pages (and most static hosts) can only serve `index.html`
for `/`, this site uses **hash-based routing**: `#/dashboard`,
`#/asset/ethereum`, `#/send`, etc. The part after `#` never leaves the
browser, so there's nothing for the server to route — `index.html` is
always what gets requested, and `js/router.js` handles the rest. No
`404.html` workaround is needed.

## Firestore data model

```
users/{uid}
  name, email, role ('user' | 'admin'), createdAt

users/{uid}/wallet/portfolio
  assets: {
    ethereum: { balance: number, address: string },
    bitcoin:  { balance: number, address: string },
    ... one entry per supported network
  }

users/{uid}/transactions/{transactionId}
  id, hash, type ('sent' | 'received' | 'gas'), asset, networkId,
  amount, usdValue, from, to, gasFee, gasFeeUsd, status
  ('confirmed' | 'pending' | 'failed'), timestamp, simulated: true
```

Every authenticated user's data lives isolated under `users/{their uid}`.
Isolation is enforced by **Firestore Security Rules**, not by client-side
checks — see `firestore.rules`.

## Setting up Firebase

1. Go to the [Firebase Console](https://console.firebase.google.com) and
   create a new project.
2. **Build → Authentication → Sign-in method** → enable **Email/Password**.
3. **Build → Firestore Database** → create a database (production mode).
4. **Project settings → General → Your apps** → add a **Web app** and
   copy the config object it gives you.
5. Open `js/firebase.js` and replace the placeholder values in the
   clearly marked `firebaseConfig` object with your own:

   ```js
   const firebaseConfig = {
     apiKey: 'YOUR_API_KEY',
     authDomain: 'YOUR_PROJECT.firebaseapp.com',
     projectId: 'YOUR_PROJECT_ID',
     storageBucket: 'YOUR_PROJECT.appspot.com',
     messagingSenderId: 'YOUR_SENDER_ID',
     appId: 'YOUR_APP_ID',
   };
   ```

   Firebase web API keys are not secret — it's normal and safe for them
   to be visible in frontend code. Real protection comes from Firestore
   Security Rules, which is why the next step matters.

6. Deploy the included **security rules**: open **Firestore Database →
   Rules** in the console, paste in the contents of `firestore.rules`,
   and click **Publish**. (Or use the Firebase CLI: `firebase deploy
   --only firestore:rules`.)

### Creating your first admin user

A user can never grant themselves the `admin` role — the security rules
explicitly block that write. To create your first admin:

1. Sign up normally through the website.
2. In the Firebase Console, open **Firestore Database → users →
   {that user's uid}**.
3. Change the `role` field from `"user"` to `"admin"`.
4. Reload the site signed in as that user — an **Admin panel** link now
   appears in the sidebar. Ordinary users never see this link, and
   navigating to `#/admin` directly redirects them away — enforced both
   in the router and in Firestore rules, so it can't be bypassed by
   editing frontend code.

## Running it locally

This is a static site, so you technically only need to open `index.html`
in a browser — but ES modules are blocked by the `file://` protocol in
most browsers, so serve it over `http://localhost` instead. Any static
file server works, for example:

```
python3 -m http.server 8000
```

or, if you have Node installed on your machine (only needed for local
testing convenience, never for the deployed site):

```
npx serve .
```

Then visit `http://localhost:8000`.

## Deploying to GitHub Pages

1. Push this repository to GitHub.
2. In the repo, go to **Settings → Pages**.
3. Under **Build and deployment**, choose **Deploy from a branch**, pick
   your default branch and the `/ (root)` folder.
4. Save. GitHub Pages will serve `index.html` directly — no build step,
   no `npm install`, no `npm run build`.

That's it:

```
git add .
git commit -m "Deploy"
git push
```

## How simulated balances work

Each user's portfolio document (`users/{uid}/wallet/portfolio`) holds a
balance and a display address for every supported network. Simulated
prices drift slightly around a fixed base price each day
(`js/pricing.js`), so portfolio value and 24h change feel alive without
needing a live market data feed.

## How simulated transactions work

- **Send** (`js/wallet.js: simulateOutgoingPayment`) validates the form,
  computes a simulated gas fee (`js/txEngine.js: calculateGasFee`),
  checks the balance covers amount + gas, deducts both, writes a
  `sent`-type transaction document, and shows a confirmation animation.
- **Receive** → **Simulate incoming payment** adds a configurable amount
  to the balance and writes a `received`-type transaction.
- The **Admin panel** can additionally generate transactions on any
  user's behalf, edit their balances directly, regenerate their
  addresses, change a transaction's status, or reset their portfolio to
  defaults.

No blockchain, signing library, or RPC provider is involved anywhere in
this flow.

## Supported networks

Ethereum, Bitcoin, Solana, Polygon, BNB Chain, Base, Arbitrum — each with
its own simulated address format, balance, and transaction history,
combined into one unified portfolio view.

## Security notes

- No Firebase Admin SDK or service-account credentials appear anywhere in
  this codebase — only the public, safe-to-expose client SDK config.
- Admin access is enforced by Firestore Security Rules (`isAdmin()` in
  `firestore.rules`), which check the requesting user's own `role` field
  server-side. Hiding the admin nav link is a UX nicety, not the security
  boundary.
- Users can never write their own `role` field to `"admin"` — rules
  explicitly compare the incoming value against the existing one for
  non-admin writers.

## What was migrated from the earlier React prototype

This static site is a full rebuild, not a renamed React build. The
business logic (address generation, simulated pricing, gas calculation,
transaction construction, portfolio math, and the Firestore data model)
was ported line-for-line into plain JavaScript modules; the UI was
rebuilt as hand-written HTML strings and DOM APIs instead of JSX, and
React Router was replaced with a small hash-based router written from
scratch for this project.
